## Phase 5: open-source handoff

**Goal:** anyone with an Anthropic API key, or a Claude subscription, or only a Mac with the local model, can reproduce the baseline, run improvement rounds, and contribute policy changes with evidence. The yardstick (judge prompts, gold data, metrics) stays maintained by the project; policy changes are community PRs.

### 5a: make it runnable by others (no model usage needed): items 1 to 5 done (2026-10-01), item 6 done but the GEPA spike
1. ✓ **`anthropic` backend** (`adapters/anthropic_llm.py`): API-key access through the official SDK, with the Message Batches API for eval replays and labeling (half price), prompt caching on the shared context prefix, the `refusal` stop reason handled with server-side fallbacks, usage recorded for the cost metric. Config: `[llm] backend = "anthropic"`. The plan guard is replaced by a dollar budget per run.
2. ✓ **Portable dataset:** `honed bundle export|import`. The bundle holds PR metadata, review threads (text, author login, URL), mechanical outcomes, judge labels, gold issues, splits and the decision log. It does **not** hold code: context packs are rebuilt locally by `honed rehydrate` from git, so no repository code is redistributed. Human labels move into `yardstick/human_labels/` because they are part of the yardstick.

Remove machine-specific defaults (absolute paths, Keychain item names become optional).
4. ✓ **Benchmark adapters:** Martian Code Review Bench and AACR-Bench as test-split sources, so contributors have Important-heavy held-out sets.
5. ✓ **Operational fixes carried over:** a maximum wait for `--wait-for-reset`, a clean interrupt that records the in-flight candidate, unbuffered progress logs.
6. ✓ (README section and `export-gold`, 2026-10-01; the GEPA spike is open) **Related work and interoperability** (survey of 2026-10-01; no existing project combines harvest + outcome judge + replay eval + gated auto-promotion): a README section naming the nearest projects honestly (Martian code-review-benchmark for evaluation, Pica for online feedback-to-rules, Qodo PR-Agent and Kodus as reviewers, GEPA as a generic prompt optimizer); `honed export-gold --format martian` so our answer keys and results are comparable with Martian's leaderboard; and a spike on using GEPA as an alternative proposer before growing our own.

### Governance (no single owner required)
- **Separate ownership:** the yardstick (`yardstick/prompts/`, gold data, `METRICS.md`, thresholds) is owned by a small maintainer group; `policy/` is open to community candidates. The same people must not change both in one change, because a score only means something while the goalposts are fixed.
- **Automated promotion on project compute:** a candidate's eval report is a claim, not a verdict. A project-run gate (CI or a bot on a project key or sponsored budget, with the fixed judge) re-evaluates each candidate and merges or rejects it by the rules. Humans handle disputes and rule changes, not routine promotions.
- **A private test split** held by the maintainers, scored on every promotion and refreshed over time, so many contributors trying many candidates against the public validation split can't overfit it unnoticed. *Built 2026-10-01:* `honed splits --assign` halves each language's test PRs into `test-public` and `test-private` (`[eval] test_private_share`), stored in the maintainers' store; `bundle export` and `export-gold` leave `test-private` out (its PRs, labels, gold and the judge's answers on them) unless `--include-private`, and the manifest records which. Its PRs are public GitHub PRs inside the published harvest window, so it guards against accidental overfitting only; refreshing it with PRs newer than any published bundle is what keeps it honest.
- **Poisoning backstop:** the self-review lens and the two-author evidence rule are mechanical; a maintainer review is the final check on a lesson that looks engineered to game the judge.
- The original owner may join the maintainer group or step back entirely; nothing in the system depends on one person.

### Data quality (planned 2026-10-07)

The rules, what is enforced today, the audits and the checklists for contributors are in `DATA_QUALITY.md`; this section records the plan.

Training and held-out data must stay high quality as more of it is added. The checks already in place: rigor-ranked source repositories, bot, backport and automation filtering, outcomes from real code changes, the addressed check, human-grounded gold provenance, per-round gold, time-ordered splits with a private test half, benchmarks as test-only, the fixed and audited judge, redaction, and lessons that need two authors' PRs. Additions:

1. **Review provenance.** Every review comment gets a provenance label: `human`, `ai_assisted`, `autonomous` or `unknown`. Each label carries a confidence and the signals that fired: platform metadata (GitHub App posting, Copilot markers, auto-generated tags, AI co-author trailers and "generated with" lines), repository AI-disclosure policies, behavior (bursts of long comments, round-the-clock cadence, templates reused across repositories, superhuman latency), and style drift from the same reviewer's pre-2023 writing (a weak signal). The classifier is calibrated on known-provenance comments (bot accounts as AI, pre-2023 comments as human), and its error rates ship with each dataset version.
2. **Fresh held-out data, gated by provenance.** The private test half and future validation refreshes use PRs created after the reviewer and judge models' training cutoff (July 2026 onward for the current models), to avoid memorization. They prefer repositories with low AI-review use; a repository whose AI-assisted share passes a threshold drops out of held-out data. The headline test score uses human-provenance gold only; other provenance classes and "human-only catches" (issues humans raised that AI reviewers on the same PR missed) are reported separately. A pre-cutoff and a post-cutoff test set are kept side by side, so the effect of memorization and of automation can each be measured.
3. **Human audits, tracked** (`METRICS.md` section 5): judge validity, gold precision and severity, the addressed check, and provenance. Each dataset version gets a blind, stratified sample per audit, labeled by at least 2 people who didn't author or review the PRs. Everything is recorded in an audit ledger (`AUDITS.md` plus `yardstick/audits/<audit-id>/`), and a dataset version is released only when its audits are complete. The labeling tool is generalized to every audit type, and anyone can contribute labels.
4. **Contamination checks**, run for every dataset version and reported in the data-quality report:
   - **Between splits:** detect the same change in two splits or in a benchmark, matched by content (normalized diff hashes and near-duplicate diffs), not by repository name: cherry-picks, ports between forks, vendored copies. Duplicates go to the earliest split, or out of held-out data entirely.
   - **Lesson evidence from train only:** a lesson that cites a validation or test PR is refused, enforced mechanically in the proposer and the gate.
   - **Model memorization probes:** for a sample of held-out PRs, give the reviewer and judge models the PR context with the human review comment withheld, and measure verbatim and near-verbatim overlap between their output and the real comment. Compare that with the same probe on post-cutoff PRs, which they can't have seen. A pre-cutoff excess means memorization: report it, and weight post-cutoff results more heavily.
   - **Keeping our data out of future models:** every published bundle and `DATASET.md` carries a unique canary string and a request not to train on the data, so later models can be checked for having trained on it. The private test half is never published, and held-out sets are refreshed with post-cutoff PRs as new models arrive.
5. **Concentration limits, enforced, not just reported.** Defaults, configurable:
   - **Per repository:** at most 15% of a split's PRs.
   - **Per PR author:** at most 5% of a split's PRs.
   - **Per reviewer:** at most 5% of a split's gold weight. A prolific reviewer's gold issues are down-weighted to the cap rather than dropped, so no data is lost, but no single reviewer defines what a real issue is.

   The caps are applied when splits are assigned and when gold weights are computed, and the data-quality report shows each split's largest shares.
6. **A data-quality report per dataset version, enforced in CI.** It covers label, severity and provenance mix per language and repository, how the splits compare, audit coverage and results, filter counts, and duplicates found.
7. **Rules for contributed data.** New repositories must meet the rigor bar; labels always come from the fixed judge, never from contributors; only maintainers add to held-out data; and each addition is a versioned dataset release with a changelog.
